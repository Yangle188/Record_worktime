## D-000 产品形态：Web PWA

**背景**：最初需求为「打卡应用，可实时联网更新时间和地点」。

**决策**：采用 Web PWA。

**理由**

- 单人自用工具，无需应用商店分发，链接即用、可安装到桌面；
- 一套代码覆盖 iOS / Android / 桌面；
- 定位 API 与地图 SDK 在浏览器端能力足够满足"打卡时刻记录一次地点"。

**被否方案**：原生 App（开发与分发成本远超收益）、微信小程序（需备案与平台审核，个人自用过重）。

---

## D-003 不做地理围栏（重要变更）

**背景**：v0.1 曾设计"进入公司范围自动打卡 + 范围校验"，用户明确澄清：**不是为了限制，只是为自己记录打卡时间**。

**决策**：删除围栏判定、自动打卡、范围外告警等全部相关需求。

**理由**

- 用户诉求是"记录"而非"约束"，围栏属于过度设计；
- 浏览器**无法可靠实现后台自动定位**（iOS Safari 切后台会冻结页面、无后台定位权限），围栏自动打卡在 Web 上只能"尽力而为"，体验不可靠；
- 删除后，本产品**最大的技术风险归零**，Web 技术栈变得完全够用。

**影响**：反作弊、审批流、管理端报表、权限矩阵等团队场景功能一并删除，产品复杂度大幅下降。

## D-004 打卡时采集一次定位

**决策**：打卡瞬间调用一次 `getCurrentPosition`，**不使用** `watchPosition` 持续追踪。

**理由**

- 需求只需要"打卡那一刻在哪"，持续追踪属于多余采集；
- 显著省电，且在 iOS 上更容易被系统与用户接受；
- 隐私最小化原则（位置属敏感个人信息，仅按需采集）。

**例外**：打卡首页需要展示"当前地址"，可在页面处于前台时以较低频率刷新展示用定位，但**不落库**。

## D-007 以联网校准的时间为准

**决策**：打卡记录的时间取「校准后的网络时间」；设备本地时间另存为参考字段并记录两者偏差。

**实现方式**：因 D-012 选定无账号、无自建服务端，改为向公共时间源发起请求并读取 HTTP `Date` 响应头，按最小 RTT 采样计算偏移量（NTP 的简化实现）；配置多个时间源按优先级降级。

**理由**

- 设备时间可被随意修改，作为工时依据不可信；
- 单人自用同样存在"手机时区 / 时间错误导致统计混乱"的现实问题；
- 无后端也能获得可信时间，成本极低。

**边界**：全部时间源不可用时降级为本地时间，但必须明确标注"未校准"，且**不篡改历史记录**。

## D-008 工时统计口径

**决策**：段（segment）为核心单元，成对闭合；日工时 = Σ 有效段时长；跨 0 点的段归属开始日；业务日边界默认凌晨 4:00，可配置。

**理由**

- 相比"首次打卡到末次打卡"的粗口径，能正确排除午休与外出时段；
- 相比"固定上下班 + 扣除午休"的班次模型，更贴合自由职业 / 远程办公的真实节奏；
- 段模型天然支持多段与按地点拆分统计。

**细则**：见 `PRD.md` §4.5（含碎片阈值、未闭合段处理）。

## D-010 地点识别策略

**结论：方案 A —— 用户自定义地点 + 最近匹配**（与本文推荐一致）

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐，已采纳）** | 用户自定义地点 + 打卡时最近匹配（半径默认 200m），未匹配可一键命名 | 可控、可命名、统计有意义 | 需要用户先建地点（首次几次打卡后即可沉淀完成） |
| B | 纯自动聚类（按距离把邻近坐标聚成一类） | 无需手动建地点 | 命名混乱（"地点 1 / 地点 2"），可解释性差 |
| C | 仅存地址字符串，不做汇总 | 实现最简单 | **无法满足"按地点汇总工时"的需求** |

**采纳理由**：汇总的前提是地点有稳定身份标识，只有 A 能同时满足"自动匹配"与"人类可读命名"。

## D-011 忘记结束打卡的处理

**结论：方案 A —— 继续计时 + 超 12h 弹窗确认 + P1 支持事后修正**（与本文推荐一致）

| 选项 | 说明 |
| --- | --- |
| **A（推荐，已采纳）** | 继续计时 + 超过 12 小时弹窗确认「还在工作吗？」+ P1 支持事后修正结束时间 |
| B | 超过阈值自动截断并标记"待确认"，由用户确认后生效 |
| C | 不处理，任其计时 |

**采纳理由**：不自动伪造工时（数据更真实），同时通过弹窗与事后修正两条路径兜底。若采用 B，需额外定义截断点（班次结束时间还是最后活动时间），对个人工具而言规则过重。

## D-012 登录方式

**结论：方案 B —— 纯本地存储，无账号**（**与本文推荐不同**，用户明确选择本地优先）

**选择理由（用户侧）**：数据完全不出设备，隐私最强；无需登录、无后端成本与运维。

**接受的取舍**

- 放弃多设备实时同步（原 M5 项），改为**备份文件迁移**；
- 放弃云端兜底，改为**主动提醒 + 一键导出 / 导入 JSON**（见 D-013）；
- 用户需自行承担浏览器清理站点数据导致丢失的风险，产品侧通过备份提醒降低概率。

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A（原推荐） | 邮箱 magic link，或 Google / Apple 一键登录 | 跨设备同步最省事，无密码管理负担 | 需要一次登录动作，数据上云 |
| **B（已采纳）** | 纯本地存储，无账号 | 隐私最佳、零后端依赖、零运维 | 换设备 / 清缓存即丢数据，无法多端同步 |
| C | 匿名账号 + 设备码 | 免登录 | 换设备需迁移码，体验略绕，账号找回困难 |

> 原推荐 A 未被采纳，理由见上方"结论"。

## D-013 存储方案变更：云服务 → 纯本地

**背景**：D-009 曾确定使用 Supabase（云服务 + 账号 + RLS）实现多设备同步；D-012 拍板选 B（纯本地存储，无账号）后，该方案不再成立。

**决策**：数据唯一存储于浏览器 **IndexedDB**（Dexie 管理），前端直连高德 API 与公共时间源，**不引入任何后端服务**。

**连带影响**

| 受影响项 | 变化 |
| --- | --- |
| 账号与鉴权 | 删除（无 Auth、无 RLS） |
| 数据同步 | 删除多设备实时同步；改为 JSON 备份文件的导出 / 导入 |
| 时间权威来源 | 由"服务端时间"改为"公共时间源（HTTP `Date` 响应头）+ 本地时间兜底" |
| 数据模型 | 移除 `user_id`、`daily_summaries` 落表；新增 `meta`（备份时间、校准偏移） |
| 数据丢失风险 | 上升（浏览器清理站点数据），需**主动备份提醒**作为兜底 |
| 里程碑 | 备份 / 恢复能力由 M5 **提前到 M1** |
| 隐私 | 增强：数据不离开设备，无上传行为 |
| 运维成本 | 降为零：仅静态托管 |

**理由**：与 D-012 的一致性优先；单人工具无需为多端同步承担账号体系与后端复杂度。

## D-014 结果呈现方式：可视化优先

**背景**：用户明确要求"打卡结果需要有可视化界面呈现"。

**决策**

1. **即时反馈**：每次打卡弹出结果卡片（时间 / 地点 / 时长 / 地图缩略图）；
2. **状态可视化**：首页环形进度展示今日目标达成度，进行中的段实时走秒 + 呼吸动效；
3. **统计图表化**：甘特式时间轴、周 / 月柱状图、地点占比环形图、日历热力图（P1）、地图打卡点分布；
4. **图表库统一用 ECharts**（`echarts` + `echarts-for-react`）：一个依赖覆盖全部所需图表类型，避免多套库混用。

**约束**：图表数据与列表明细必须由**同一份汇总函数**产出，杜绝"图表与明细对不上"（已纳入验收标准）。

## D-015 M1 范围调整：只记录坐标

**背景**：TECH-DESIGN 评审期间确认，M1 不必等到地图 Key 配置完成，先把「时间 + 坐标」的记录闭环做扎实。

**决策**：M1 **不接入**逆地理编码与地图渲染；打卡只记录 `lat/lng/accuracy`：

- 打卡结果卡片（V-1）在 M1 **不含**地图缩略图与地址文字，改为展示坐标 + 定位精度 + 是否关联地点；
- `GeocodeProvider` 仅落地**接口 + 空实现**（`NoopGeocodeProvider`，返回不可用），保留可替换性（PRD §6）；
- 逆地理地址（L-3）、地图缩略图（L-4 / V-6）顺延至 **M3 地点体系**一并落地。

**理由**

- 地图 / 逆地理依赖高德 Key 与域名白名单，属于外部阻塞项，不应阻塞打卡核心（PRD §9 Key 风险）；
- 「记录坐标」已完整满足 M1 的交付标志（能记录一天的多段打卡 + 数据可导出）；
- provider 接口先行落地，M3 只需替换实现，不产生返工。

**影响**

- M1 的「实时地点显示」降级为「实时坐标显示」；
- PRD §4.3 的 L-3 / L-4、§4.7 的 V-1 含地图缩略图部分、V-6 顺延到 M3；
- PRD 验收标准 #2 中「地图缩略图」一项在 M1 不做，M3 补齐。
